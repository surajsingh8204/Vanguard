# Vanguard Pipeline Orchestrator

The `pipeline` package is an execution layer over the existing Vanguard
engines. It does not contain clustering, retrieval, forecasting, evaluation,
or report-generation business logic.

## Run

From the repository root:

```bash
conda activate vanguard
python pipeline/run_pipeline.py
```

Validate configuration without downloading data or loading ML models:

```bash
python pipeline/run_pipeline.py --dry-run
```

An interrupted run resumes automatically:

```bash
python pipeline/run_pipeline.py
```

Restart without incomplete orchestration state:

```bash
python pipeline/run_pipeline.py --no-resume
```

Rerun one stage and all stages after it:

```bash
python pipeline/run_pipeline.py --from-stage model_build
```

Valid stage names are:

- `ingestion`
- `preprocessing`
- `model_build`
- `analytics_artifacts`
- `validation`

## Docker

Build and run the independent pipeline service:

```bash
docker compose build pipeline
docker compose run --rm pipeline
```

The service does not start or modify the FastAPI backend. Use the root
`compose.yaml` for the pipeline service. The legacy
`docker/docker-compose.yml` file remains PostgreSQL-only.

It mounts:

- `data_lake/` for raw and processed data
- `core/artifacts/` for application artifacts and the FAISS index
- `artifacts/` for orchestration checkpoints and logs
- a named Hugging Face model cache

After a successful pipeline run, restart the FastAPI process. Artifact-backed
dashboard endpoints reread files, but `/query` keeps an in-memory
`AIPipeline` singleton and will not pick up a new FAISS index until restart.

| Embeddings | `core.embeddings.embedding_services.EmbeddingService` |
| Main clustering | `core.clustering.hdbscan_cluster.HDBSCANClusterer` |

There is no dedicated entity-analysis engine in the current repository, so the
orchestrator does not invent one. Entity-related information remains whatever
the existing labels, graph, metadata, and intelligence engines already emit.

## Execution flow

1. **Ingestion**
   - Uses the existing GDELT engine one feed at a time.
   - Deduplicates URLs and writes bounded JSON batch checkpoints.
   - Stops at `ingestion.articles_limit` or when configured feed history is
     exhausted.
2. **Preprocessing**
   - Uses the existing `ContentPipeline.process_batch` method.
   - Reuses fetch, extraction, purification, quality, and metadata engines.
   - Appends accepted records to resumable JSONL state after every batch.
   - Streams JSONL into the canonical processed JSON array without retaining
     the full processed corpus in memory.
3. **Embeddings, clustering, and vector database**
   - Uses the existing `AIPipeline.build_vector_db`.
   - Embeddings execute in configured batches with per-batch `.npy`
     checkpoints.
   - The existing core performs clustering before final FAISS creation because
     `VectorStore` metadata requires cluster and subcluster IDs. Reversing these
     two operations would change vector-search semantics, so the orchestrator
     preserves the repository's real dependency order.
4. **Narrative intelligence, evaluation, and artifacts**
   - Uses the existing `AIPipeline.run_analytics`.
   - Updates timelines, spikes, evolution, graphs, influence, forecasts,
     warnings, evaluation metrics, briefs, strategic context, and all artifact
     files generated by the core.
5. **Validation**
   - Fails the run if any configured required artifact is missing or empty.

## Checkpoints and resume

Orchestration state is written atomically to:

```text
artifacts/pipeline/pipeline_state.json
```

Other resumable data:

```text
artifacts/pipeline/ingestion/batch_*.json
artifacts/pipeline/preprocessing/accepted_articles.jsonl
artifacts/pipeline/embeddings/batch_*.npy
artifacts/pipeline/embeddings/manifest.json
```

Completed stages are skipped after an interrupted run. Once a full run
completes, invoking the command again archives the previous state and starts a
new run.

## Configuration

Edit `pipeline/config.yaml`. It controls:

- target article count and feed history
- automatic or explicit ETL batch sizes
- worker count
- embedding model, batch size, device, and checkpoints
- FAISS rebuild behavior
- artifact rebuild and validation
- rotating file/console logging

`device: auto` delegates device choice to Sentence Transformers. Use `cpu`,
`cuda`, or another supported device explicitly when required.

## Failure behavior

Every stage is isolated in the state file. On failure the command:

1. logs the complete traceback to `artifacts/pipeline/logs/pipeline.log`;
2. records the failed stage and error in `pipeline_state.json`;
3. exits non-zero with the failed stage and cause;
4. tells the operator to rerun the same command after fixing the cause.

Exceptions are never silently swallowed by the orchestration layer.
